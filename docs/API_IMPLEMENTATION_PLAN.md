# План: API до Transaction / Transfer / Attachment

Документ описує **поточний стан** репозиторію `finance-tracker` і **порядок кроків**, які ти реалізуєш сам (валідація, сервіси, роути, файли, помилки, тести). Стек: Express 5, Prisma (PostgreSQL), Zod, Pino, Jest.

**Аутентифікацію (логін, JWT, cookies, мідлвар перевірки токена)** цей план **не ставить у твій обов’язок** — про неї є окремий розділ: _як узгодити контракт_, щоб твій код не ламався, коли auth з’явиться з іншого боку.

## Що ще треба зробити (твоя зона)

Це те, без чого **немає повноцінного REST** поверх уже наявних моделей:

- Узгоджений шар **помилок** під існуючий `errorHandler` (щоб клієнт отримував передбачувані `statusCode` і `code`).
- **Zod-схеми** для кожного типу вхідних даних (body, query, params маршруту).
- **Сервіси** — правила «чи можна так зберегти», «чи цей рахунок того ж користувача», атомарність переказу тощо; репозиторії лише виконують збереження/читання.
- **HTTP-handlers + роути** — тонкий шар: витягнути вхід → перевалідувати → викликати сервіс → віддати JSON.
- Для **Attachment**: **зберігання файлу** (не лише рядок у БД) + обмеження розміру/MIME + узгодження з `storageKey` у Prisma.
- **Інтеграційні тести** на happy path і типові помилки (без обов’язкового реального JWT, див. розділ про auth).
- За бажанням команди: **OpenAPI/Swagger** поверх тих самих Zod-схем.

## Аутентифікація — не твоя зона: як ти маєш це «опрацювати»

Тут **не план реалізації логіну**, а **як не залежати від неї жорстко** і не блокувати Transaction/Transfer/Attachment.

### Що мається на увазі під «не моя зона»

Хтось інший (або інший етап) відповідає за: видачу токенів, зберігання refresh, мідлвар, який перевіряє підпис і термін, оновлення `req.user` / сесії. Ти не пишеш це в рамках цього плану, якщо так домовлено в команді.

### Як ти все одно будуєш свій шар коректно

1. **Контракт на вхід у сервіс**  
   Сервіси не повинні читати `Authorization` самі. Вони приймають **явний аргумент** на кшталт `actingUserId: string` (або об’єкт `context: { userId }`), який _хтось_ передасть з HTTP-шару. Тоді коли з’явиться справжній auth-мідлвар, handler просто зробить: `userId = req.user.id` замість заглушки.

2. **Заглушка в dev / у тестах**  
   Поки немає мідлварі: для локальної розробки можна тимчасово передавати фіксований `userId` з env (наприклад `DEV_USER_ID`) **лише якщо команда це дозволяє** — або в інтеграційних тестах підставляти `userId` напряму в виклик сервісу / через supertest з заголовком, який мок-мідлвар перетворює на `req.user`. Суть: **твої сервіси не знають**, звідки взявся `userId`.

3. **Роутинг**  
   У `v1/index.ts` ти можеш змонтувати роути **без** auth-мідлварі спочатку; коли колега додасть `authenticate`, він обгорне той самий router або окремі шляхи. Твої файли роутів не повинні містити логіки перевірки JWT — лише виклик handler’а.

4. **Документування очікувань**  
   Коротко в README або в коментарі до `v1`: «ендпоінти розраховані на те, що upstream-мідлвар виставить `req.user`» — це **контракт для людини**, яка робить auth.

5. **Авторизація (ownership)**  
   Навіть коли auth зробить хтось інший, **перевірка «цей `accountId` належить цьому `userId`»** зазвичай лишається в **твоєму сервісі** (це вже не «хто залогінений», а «чи можна чіпати цей ресурс»). Тобто: JWT — не ти; **зв’язок сутності з користувачем** — частина твоєї бізнес-логіки.

## Порядок реалізації (детально, що мається на увазі кожним пунктом)

Нижче кожен пункт розписаний так: **що робиш**, **навіщо**, **де це живе в архітектурі**.

---

### Крок 1. Помилки API та (за бажанням) формат успішних відповідей

**Що робиш.** Вводиш невеликий набір типів помилок (класи або фабрики), у яких завжди є хоча б:

- `statusCode` — HTTP-статус (400, 404, 409, 403…);
- `code` — стабільний машиночитаний ідентификатор (`VALIDATION_ERROR`, `NOT_FOUND`, …);
- `message` — людиночитаний текст (для логів і інколи для клієнта).

**Навіщо.** У `src/middleware/errorHandler.ts` уже закладено контракт: він читає `statusCode` і `code` з об’єкта помилки. Якщо кидати «голі» `Error` або сирі помилки Prisma, клієнт отримає непередбачувані відповіді й ризиковане розкриття деталей у production.

**Що мається на увазі під «формат успішних відповідей».** Домовитися, чи обгортаєш дані в `{ data: ... }`, як виглядає пагінація (`items`, `total`, `page` тощо). Це не обов’язково на старті, але якщо не зафіксувати — фронт отримає різні форми з різних ендпоінтів.

**Залежності.** Немає; можна робити першим паралельно з чимось іншим.

---

### Крок 2. Zod-схеми для вхідних даних (per endpoint)

**Що робиш.** Для кожної операції (створити транзакцію, оновити, список з фільтрами, створити переказ, завантажити метадані вкладення) описуєш **окремі схеми** для:

- **body** — JSON тіла;
- **query** — рядки з URL (сторінка, ліміт, дати, фільтри);
- **params** — `id` у шляху, `transactionId` якщо nested.

**Навіщо.** Express дає «сирий» `req.body` / `req.query` без гарантій типів. Zod перетворює це на **валідований об’єкт** і одразу відсікає сміття до сервісу. Один раз узгоджуєш правила (наприклад `amount` як string для Decimal) — далі сервіс не розбирається з рядками з URL.

**Що мається на увазі під «спільні схеми».** Пагінація (`page`/`limit` або cursor), спільний формат дат (`occurredAt` з ISO-рядка), обмеження на `direction` enum — виносиш у маленькі переіспользувані шматки, щоб списки транзакцій і переказів не дублювали однакові поля.

**Залежності.** Крок 1 корисний для мапінгу помилок Zod у 400 з єдиним `code`.

---

### Крок 3. Сервіси: Transaction → Transfer → Attachment

**Що робиш.** Класи або функції, які приймають **вже валідовані** дані + **`actingUserId`** (або контекст з кроку «auth не твоя зона») і викликають репозиторії.

**TransactionService — що мається на увазі.**

- Створення/оновлення: перевірити, що `accountId` (і за потреби `categoryId`) належать **тому ж** `userId`, що й транзакція; що `currencyId` відповідає правилам продукту (часто — валюта рахунку).
- Напрямок `INCOME` / `EXPENSE` і наявність категорії — узгодити з бізнес-правилами (наприклад expense без категорії — ок чи ні).
- Список: делегувати в репозиторій фільтри, які вже є в `ITransactionRepository`, не дублювати SQL у сервісі без потреби.

**TransferService — що мається на увазі.**

- Обидва рахунки `from` / `to` мають бути **користувача** `actingUserId`.
- За домовленістю: заборона однакових рахунків, перевірка валюти, мінімальна сума.
- **Атомарність:** створення запису `Transfer` у БД має бути узгоджене з тим, чи ви **також** створюєте дві `Transaction` (доходи/витрати) — якщо так, це одна **транзакція Prisma** (`$transaction`), щоб не залишити півстану.

**AttachmentService — що мається на увазі.**

- Перевірити, що `transactionId` існує і належить користувачу.
- Порядок: спочатку надійне збереження файлу в storage, потім запис рядка в БД (або навпаки з компенсацією — головне не мати «сирот» файлів без запису і навпаки).
- Видалення: прибрати з БД (soft delete, як у вас прийнято) + видалити blob за `storageKey`.

**Залежності.** Репозиторії вже є; Zod (крок 2) — логічно перед handlers, але сервіси можна писати, приймаючи «чисті» типи вручну, поки роути не готові.

---

### Крок 4. Інфраструктура файлів (storage) для Attachment

**Що робиш.** Інтерфейс на кшталт: згенерувати ключ, зберегти буфер/стрим, прочитати, видалити. Імплементація для dev — локальна папка; для prod — пізніше S3-совместимий бекенд без зміни сервісу, лише інша імплементація.

**Навіщо.** У Prisma `Attachment` зберігає `storageKey`, `mimeType`, `originalName` — **не сам файл**. Файл має жити в сховищі; репозиторій — лише метадані.

**Що мається на увазі під обмеженнями.** Максимальний розмір, whitelist MIME — або в мідлварі multipart, або одразу після парсингу в handler з викиданням своєї помилки з кроку 1.

**Залежності.** Логічно після або паралельно з `AttachmentService`, але до продакшен-роута upload.

---

### Крок 5. HTTP-handlers і роути v1

**Що робиш.**

- Файли роутів: наприклад `transactions.routes.ts`, `transfers.routes.ts`, `attachments.routes.ts` (назви на смак команди).
- У кожному handler: дістати `body`/`query`/`params` → `schema.parse()` або safeParse з мапінгом у 400 → виклик відповідного методу сервісу → `res.status(...).json(...)`.
- У `src/routes/v1/index.ts`: `router.use('/transactions', transactionsRouter)` тощо.

**Навіщо.** Роут має залишатися **тонким**: без бізнес-правил і без прямих викликів Prisma, інакше дублювання й неможливі тести сервісу окремо від HTTP.

**Що мається на увазі під nested маршрутами.** Оскільки `Attachment` у схемі прив’язаний до транзакції, зручно мати шлях на кшталт `POST /transactions/:transactionId/attachments` — тоді `transactionId` у params і валідації, а не в тілі.

**Залежності.** Кроки 1–4; контракт `actingUserId` з розділу про auth.

### Крок 6. Мідлварі: що куди (уточнення під ваш `app.ts`)

**Глобальний стек уже є** у `createApp()`: не дублювати CORS/Helmet на v1 без потреби.

**Що ти додаєш локально до фіч:**

| Місце                   | Що мається на увазі                                                                                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Тільки на upload-роутах | Парсинг `multipart/form-data` (окремий пакет), ліміт розміру полів. **Не** заміняти глобальний `express.json` на multipart для всього API.                                |
| На конкретних router’ах | Коли з’явиться auth від колеги — їхній мідлвар **перед** твоїми handlers; твій код не змінює принцип роботи, лише отримує заповнений `req.user` (або ти лишаєш заглушку). |
| У handler               | Валідація Zod після того, як body вже розпарсено відповідним middleware.                                                                                                  |

---

### Крок 7. Тести

**Що робиш.**

- **Інтеграційні (supertest):** повний шлях через Express до сервісу/БД (або test DB) для створення транзакції, списку, переказу, помилок 400/404.
- **Без реального JWT:** або тестовий `app` з мок-мідлвар «виставив `req.user`», або виклик сервісу напряму в юніт-тесті з фейковим `userId`.

**Навіщо.** Репозиторії вже покриті; тепер перевіряється **контракт HTTP + сервіс**, де найчастіші регресії.

**Що мається на увазі для Attachment.** Мок `IFileStorage` або тимчасова директорія + очищення після тесту.

**Залежності.** Після кроку 5; частково можна раніше, тестуючи сервіси ізольовано.

### Крок 8. OpenAPI / Swagger (опційно)

**Що робиш.** Якщо команді потрібна дока для фронту: з тих самих Zod-схем (у вас у залежностях є `zod-to-openapi`) генерувати опис ендпоінтів і віддати через `swagger-ui-express`.

**Навіщо.** Один джерело правди: валідація й документація не роз’їжджаються.

**Залежності.** Після стабілізації схем і шляхів (крок 2 + 5).

## Чеклист папок (орієнтир, без жорсткої прив’язки до назв)

- `src/errors/` — помилки з `statusCode` + `code` під `errorHandler`.
- `src/validation/` або `src/schemas/` — Zod для body/query/params.
- `src/services/` — Transaction / Transfer / Attachment (і за потреби інтерфейси для тестів).
- `src/storage/` — контракт + імплементація файлового сховища.
- `src/routes/v1/*.ts` + оновлений `src/routes/v1/index.ts`.
- `src/http/` або `src/controllers/` — handlers, якщо не хочеш тримати їх у файлі поруч з `Router`.

**Не обов’язково від тебе:** `src/middleware/authenticate.ts` — лише якщо команда перенесе auth на тебе; інакше ти лише **споживаєш** результат чужого мідлвару в handler (або заглушку в dev).

## Примітка по Prisma: Attachment і Transaction

У схемі `Attachment` завжди має `transactionId`. Тому в API логічно тримати створення вкладення **в контексті транзакції** (nested URL або обов’язкове поле в body з тією ж перевіркою ownership). Якщо колись знадобляться файли без транзакції — це окрема зміна схеми й міграція, не частина першого випуску цього плану.
