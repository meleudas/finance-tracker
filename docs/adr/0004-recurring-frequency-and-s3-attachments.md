# ADR 0004: Таблиця RecurringFrequency та S3-ключі для Attachment

## Status

Accepted

## Context

Потрібна підтримка **користувацьких шаблонів періодичності** для регулярних операцій (не лише фіксований enum) і **зберігання вкладень** до транзакцій без прив’язки до конкретного хмарного провайдера в схемі БД.

## Decision

1. **RecurringFrequency** — окрема таблиця на користувача з полями `name`, `every`, `unit` (`RecurringIntervalUnit`: DAY, WEEK, MONTH, YEAR). Правило `RecurringRule` посилається на запис частоти через `frequencyId` і зберігає `nextRunAt` для планувальника.
2. **Attachment** — у БД зберігається **`storageKey`** (ключ об’єкта в S3-сумісному сховищі). Поле **`url` не зберігається**: публічні або presigned URL генеруються при видачі клієнту.

## Consequences

**Плюси:**

- Гнучкі іменовані періодичності без зміни enum у міграціях.
- Стабільний ідентифікатор файлу в сховищі; зміна CDN/домену не вимагає масового оновлення БД.

**Мінуси:**

- Потрібна логіка створення бакета, upload і генерації URL у сервісному шарі.
- Для `RecurringRule` доводиться узгоджувати `currencyId` з валютою рахунку на рівні застосунку (явний FK у схемі, валідація в коді).

## Alternatives considered

- **Лише enum частоти** — відхилено: не покриває «кожні N тижнів/місяців» з іменами користувача.
- **Зберігати `url` у Attachment** — відхилено: дублювання та застарівання посилань (presigned expiry, зміна базового URL).
